Concepts before commands

Dockerfiles are build instructions, not deployment manifests.

Each instruction can affect layers, cache reuse, and image content.

The build context matters because Docker can only copy files included in that context.

Field note: Do not just run the command. Read the output. Docker teaches you a lot through container names, IDs, ports, status, logs, image tags, and inspect output.

Hands-on lab

Common instructions

FROM nginx:1.27
WORKDIR /app
COPY . /app
RUN echo build step
ENV APP_ENV=lab
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Create .dockerignore

.git
.env
*.key
*.pem
node_modules
*.log
tmp

Inspect image history

docker build -t dockerfile-practical-lab:1.0 .
docker history dockerfile-practical-lab:1.0
docker image inspect dockerfile-practical-lab:1.0

Troubleshooting checks

  • Check command output instead of assuming success.
  • Use docker ps -a when something disappears.
  • Use docker logs for app output.
  • Use docker inspect for configuration details.
  • Clean up lab artifacts after testing.

Common mistakes

  • Skipping validation commands.
  • Using latest casually for repeatable work.
  • Leaving containers, volumes, or networks behind.
  • Copying secrets into files or images.
  • Confusing host paths with container paths.

Where this fits in real environments

In real environments, Dockerfiles should be reviewed like source code because they define what enters the runtime artifact.
