Concepts before commands

Container security starts with the image. If the image contains vulnerable packages, secrets, or unnecessary tools, every container created from it inherits that risk.

Security is not one setting. It is a build, registry, runtime, and operations process.

Scanning helps find known vulnerabilities, but scanning alone does not make an image safe.

Field note: Do not just run the command. Read the output. Docker teaches you a lot through container names, IDs, ports, status, logs, image tags, and inspect output.

Hands-on lab

Create .dockerignore

.git
.env
*.key
*.pem
secrets*
node_modules
*.log
tmp

Inspect image history

docker pull nginx:1.27
docker history nginx:1.27
docker image inspect nginx:1.27

Run with read-only filesystem concept

docker run --name readonly-lab -d --read-only -p 8088:80 nginx:1.27
docker ps

Some images may need writable paths; this is a concept check.

Clean up

docker stop readonly-lab
docker rm readonly-lab

Troubleshooting checks

  • Check command output instead of assuming success.
  • Use docker ps -a when something disappears.
  • Use docker logs for app output.
  • Use docker inspect for configuration details.
  • Clean up lab artifacts after testing.

Common mistakes

  • Skipping validation commands.
  • Using latest casually for repeatable work.
  • Leaving containers, volumes, or networks behind.
  • Copying secrets into files or images.
  • Confusing host paths with container paths.

Where this fits in real environments

Real environments pair image hygiene with registry controls, CI scanning, patch processes, least privilege runtime settings, secrets management, and monitoring.
