Deploying a Wazuh Agent DaemonSet

Deploy a real Wazuh agent into Kubernetes using a DaemonSet pattern, connect it to the Wazuh manager service, validate enrollment, troubleshoot startup issues, and document what the agent can and cannot see.

Lab note: Wazuh supports Kubernetes agent deployment patterns such as DaemonSet and sidecar. This first lab uses the DaemonSet model because it is the clearest way to monitor cluster nodes in a small Kubernetes SOC lab.

Step 1: Confirm the Wazuh platform is healthy

Do not deploy agents until the Wazuh manager, indexer, dashboard, and persistent storage are healthy. Agents depend on the manager for enrollment and communication. 

kubectl get pods -n wazuh
kubectl get svc -n wazuh
kubectl get pvc -n wazuh

You want the indexer, manager master, manager worker, and dashboard pods to be Running and Ready, and the PVCs to be Bound.

Do not continue yet: If a manager pod shows CrashLoopBackOff, a rising restart count, OOMKilled, or Exit Code 137, stop and fix the Wazuh platform before deploying agents.

Stable platform checklist

Expected before continuing:
- wazuh-indexer-0: 1/1 Running
- wazuh-manager-master-0: 1/1 Running
- wazuh-manager-worker-0: 1/1 Running
- wazuh-dashboard: 1/1 Running
- PVCs: Bound
- Restart counts: not actively increasing

Step 2: Identify the manager service the agent will use

The agent needs a network address for the Wazuh manager. Inside Kubernetes, pods can use Kubernetes DNS names instead of external IP addresses. 

kubectl get svc -n wazuh

In this lab, the agent will communicate with the Wazuh manager service inside the cluster. The service named wazuh exposes the manager/authd side for the master. The service named wazuh-workers exposes agent event traffic to workers.

Local lab note: Services may show EXTERNAL-IP <pending> in a local cluster. That does not block in-cluster communication. Pods can still use Kubernetes DNS service names.

Step 3: Decide the in-cluster manager address

For this lab, the Wazuh manager address will be: 

wazuh.wazuh.svc.cluster.local

This value is not applied by itself in Step 3. You will set it inside the DaemonSet YAML file in Step 6 as environment variables on the Wazuh agent container. 

- name: WAZUH_MANAGER
  value: "wazuh.wazuh.svc.cluster.local"
- name: WAZUH_REGISTRATION_SERVER
  value: "wazuh.wazuh.svc.cluster.local"
Operator note: Step 3 is a design decision. Step 6 is where you actually place the value in the Kubernetes manifest.

Optional DNS check

Before deploying the agent, you can confirm that Kubernetes DNS resolves the Wazuh manager service from another namespace. 

kubectl create namespace wazuh-agents --dry-run=client -o yaml | kubectl apply -f -

kubectl run dns-test -n wazuh-agents --image=busybox:latest --restart=Never -- sleep 3600
kubectl exec -n wazuh-agents dns-test -- nslookup wazuh.wazuh.svc.cluster.local
kubectl delete pod -n wazuh-agents dns-test

Step 4: Create an agent namespace

Keep the agent deployment separate from the Wazuh platform namespace. This makes troubleshooting and cleanup easier. 

kubectl create namespace wazuh-agents --dry-run=client -o yaml | kubectl apply -f -

Verify the namespace exists: 

kubectl get namespace wazuh-agents

Step 5: Create the enrollment password secret

The Wazuh Kubernetes deployment creates a secret named wazuh-authd-pass in the wazuh namespace. The agent namespace needs access to the same enrollment password, so create a matching secret in wazuh-agents.

Confirm the source secret exists

kubectl get secret -n wazuh wazuh-authd-pass

Copy the secret value into the agent namespace

From PowerShell, read the existing secret value, decode it, and create the same secret key in the agent namespace. 

$EncodedAuthdPass = kubectl get secret wazuh-authd-pass -n wazuh -o jsonpath="{.data.authd\.pass}"
$AuthdPass = [System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String($EncodedAuthdPass))

kubectl create secret generic wazuh-authd-pass -n wazuh-agents --from-literal=authd.pass=$AuthdPass --dry-run=client -o yaml | kubectl apply -f -

Verify the agent namespace secret

kubectl get secret -n wazuh-agents wazuh-authd-pass
Security note: Do not hardcode real passwords into public training repos. In this lab, the manifest references a Kubernetes Secret instead of putting the password directly in the YAML file.

Step 6: Create the Wazuh agent DaemonSet manifest

Create the DaemonSet YAML file on your workstation in the Wazuh Kubernetes working directory. Do not place this directly inside the upstream Wazuh deployment folders. Keep your lab-created manifests in a separate folder so it is obvious what came from Wazuh and what you added for the lab.

Create a local lab manifest folder

From PowerShell: 

cd C:\k8s\wazuh-kubernetes
New-Item -ItemType Directory -Force .\lab-manifests

Create the DaemonSet YAML file

notepad .\lab-manifests\wazuh-agent-daemonset.yaml

Paste the manifest below into Notepad, save it, and close the file.

Where the Step 3 value goes: The manager address from Step 3 is set in this file under the container env section as WAZUH_MANAGER and WAZUH_REGISTRATION_SERVER. 
apiVersion: v1
kind: ServiceAccount
metadata:
  name: wazuh-agent
  namespace: wazuh-agents
---
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: wazuh-agent
  namespace: wazuh-agents
  labels:
    app: wazuh-agent
spec:
  selector:
    matchLabels:
      app: wazuh-agent
  template:
    metadata:
      labels:
        app: wazuh-agent
    spec:
      serviceAccountName: wazuh-agent
      tolerations:
        - operator: Exists
      containers:
        - name: wazuh-agent
          image: wazuh/wazuh-agent:4.14.5
          imagePullPolicy: IfNotPresent
          env:
            - name: WAZUH_MANAGER
              value: "wazuh.wazuh.svc.cluster.local"
            - name: WAZUH_REGISTRATION_SERVER
              value: "wazuh.wazuh.svc.cluster.local"
            - name: WAZUH_AGENT_NAME
              valueFrom:
                fieldRef:
                  fieldPath: spec.nodeName
            - name: WAZUH_AGENT_GROUP
              value: "kubernetes"
            - name: WAZUH_REGISTRATION_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: wazuh-authd-pass
                  key: authd.pass
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 300m
              memory: 512Mi
          securityContext:
            runAsUser: 0
          volumeMounts:
            - name: var-log
              mountPath: /var/log
              readOnly: true
            - name: os-release
              mountPath: /host/etc/os-release
              readOnly: true
      volumes:
        - name: var-log
          hostPath:
            path: /var/log
            type: Directory
        - name: os-release
          hostPath:
            path: /etc/os-release
            type: File

Verify the file exists

Get-Item .\lab-manifests\wazuh-agent-daemonset.yaml

Preview what Kubernetes will receive

kubectl apply --dry-run=client -f .\lab-manifests\wazuh-agent-daemonset.yaml
Best-practice note: This lab manifest is intentionally limited. It mounts host logs read-only and avoids broad host filesystem access. A production DaemonSet requires a deeper review of privileges, hostPath mounts, update strategy, node selectors, tolerations, resource limits, and organizational policy.

Step 7: Apply the DaemonSet

Apply the manifest from the location where you created it. 

kubectl apply -f .\lab-manifests\wazuh-agent-daemonset.yaml

Step 8: Verify the DaemonSet exists

kubectl get daemonset -n wazuh-agents
kubectl get pods -n wazuh-agents -o wide

In a single-node lab, expect one Wazuh agent pod. In a multi-node lab, expect one agent pod per schedulable node.

Step 9: Watch the agent logs

Get the agent pod name: 

kubectl get pods -n wazuh-agents

Then check logs by label: 

kubectl logs -n wazuh-agents -l app=wazuh-agent --tail=100

Look for messages that indicate the agent is connecting to the manager and enrolling successfully.

Step 10: Troubleshoot agent startup

Image pull failure

kubectl describe pod -n wazuh-agents <agent-pod-name>

Confirm the image tag exists and the node can pull from the registry.

Secret error

kubectl get secret -n wazuh-agents wazuh-authd-pass
kubectl describe pod -n wazuh-agents <agent-pod-name>

If the secret or key name is wrong, the pod may not start or the environment variable may not populate.

Manager connection or DNS error

kubectl run dns-test -n wazuh-agents --image=busybox:latest --restart=Never -- sleep 3600
kubectl exec -n wazuh-agents dns-test -- nslookup wazuh.wazuh.svc.cluster.local
kubectl delete pod -n wazuh-agents dns-test

If DNS fails, troubleshoot cluster DNS or service naming before troubleshooting Wazuh enrollment.

Agent pod starts but does not enroll

kubectl logs -n wazuh-agents -l app=wazuh-agent --tail=200
kubectl get svc -n wazuh
kubectl get endpoints -n wazuh

Confirm the manager service has endpoints, the manager pods are healthy, and the registration password secret matches what the manager expects.

Step 11: Verify the agent in the Wazuh dashboard

Open the Wazuh dashboard and navigate to the agent management or agent summary view. Confirm the Kubernetes node agent appears. 

Expected evidence:
- Agent visible in Wazuh
- Agent name matches the Kubernetes node name or configured agent name
- Agent status is active
- Agent group is kubernetes, if configured
- Recent keepalive or event timestamp is present

Step 12: Generate a safe node-level test event

Generate a simple lab event. Keep this benign and documented. 

kubectl run soc-agent-test -n wazuh-agents --image=busybox:latest --restart=Never -- sh -c "echo Wazuh agent DaemonSet lab test && sleep 30"

kubectl logs -n wazuh-agents soc-agent-test

kubectl delete pod -n wazuh-agents soc-agent-test

Then search the Wazuh dashboard around the timestamp of the test. Depending on agent configuration and collected log paths, this may show directly as an event or may support timing correlation.

Answer key
  1. Inside the DaemonSet YAML file under the Wazuh agent container env section.
  2. It keeps lab-created manifests separate from the upstream Wazuh deployment files and makes cleanup easier.
  3. It schedules one agent on each node, which is useful for node-level monitoring.
  4. Agents must connect to a working manager and the platform must be able to process data.
  5. It separates monitoring agents from the Wazuh platform and simplifies cleanup/troubleshooting.
  6. It avoids putting the password directly in the manifest.
  7. The DaemonSet is scheduling as expected across available nodes.
  8. Pods can communicate through ClusterIP/DNS service names inside the cluster.
  9. Cluster DNS, service name, namespace, and service existence.
  10. Host mounts affect security boundaries and visibility.
  11. Agent visible and active in the Wazuh dashboard with recent communication.
  12. Because no alert may mean no collection, not no issue.
