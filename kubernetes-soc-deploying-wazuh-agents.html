Deploying Wazuh Agents in Kubernetes

Understand Wazuh agent deployment models in Kubernetes, including DaemonSet and sidecar patterns, and validate agent visibility.

Lab objective

Understand Wazuh agent deployment models in Kubernetes and validate whether monitored sources are visible in Wazuh.

Agent deployment models

  • DaemonSet model: one agent runs on each node for broad node/container activity visibility.
  • Sidecar model: an agent runs alongside a specific application pod to monitor that application.
  • Endpoint model: agents run on servers, desktops, or VMs outside Kubernetes.

Why the model matters

Agent placement determines visibility. A DaemonSet may provide broad node coverage. A sidecar is narrower but tied to a specific workload. Endpoint agents cover machines outside the cluster. A SOC analyst should understand what is monitored and what is not.

Validation commands

kubectl get daemonset -A
kubectl get pods -A -o wide
kubectl get pods -n wazuh-daemonset
kubectl logs -n wazuh-daemonset <agent-pod-name>
kubectl describe pod -n wazuh-daemonset <agent-pod-name>

What to document

  • Agent model used
  • Namespace used
  • Covered nodes or workloads
  • Uncovered nodes or workloads
  • Agent registration method
  • Evidence that agents are reporting
Analyst note: If you do not know the monitoring coverage model, you cannot interpret alert absence. No alert may mean no detection, no event, or no collection.
