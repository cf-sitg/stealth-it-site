Windows Host Monitoring

Installing a Wazuh Agent on the Windows Host

Extend the Kubernetes SOC lab by installing a Wazuh agent on the Windows host that runs the lab. You will expose the Wazuh manager ports through kubectl port-forward, install the Windows agent, verify enrollment, generate safe Windows telemetry, and compare Windows host visibility with Kubernetes agent visibility.

Before you start

This lesson assumes the Wazuh platform is healthy and the Kubernetes DaemonSet agent is already active in the Wazuh dashboard. 

kubectl get pods -n wazuh
kubectl get pods -n wazuh-agents
kubectl get svc -n wazuh

You should already have one active Kubernetes endpoint in Wazuh before adding the Windows host.

Step 1: Understand the network problem

The Wazuh services inside Kubernetes have internal DNS names such as: 

wazuh.wazuh.svc.cluster.local
wazuh-workers.wazuh.svc.cluster.local

Those names work from pods inside the Kubernetes cluster. They do not work from the Windows host, because Windows is outside the cluster network.

Important: Do not configure the Windows agent with wazuh.wazuh.svc.cluster.local. That address is only valid inside Kubernetes.

Step 2: Check the Wazuh service ports

From PowerShell, check the Wazuh services: 

kubectl get svc -n wazuh

In this lab, the important ports are:

  • 1515/TCP for agent enrollment/registration through the wazuh service.
  • 1514/TCP for agent event traffic through the wazuh-workers service.

Your service output may also show NodePorts such as 31124 for registration and 30308 for worker event traffic. In a kind-on-Windows lab, those NodePorts may not be reachable directly from Windows.

Step 3: Test whether NodePort access works from Windows

First test localhost NodePort access: 

Test-NetConnection 127.0.0.1 -Port 31124
Test-NetConnection 127.0.0.1 -Port 30308

Then check the kind node IP: 

kubectl get nodes -o wide

Test the node IP and NodePorts: 

Test-NetConnection <kind-node-ip> -Port 31124
Test-NetConnection <kind-node-ip> -Port 30308

If these tests fail, that is not a Wazuh problem. It means the Windows host cannot reach those Kubernetes NodePorts directly.

Your lab result: In this kind-on-Windows lab, direct tests to 127.0.0.1:31124, 127.0.0.1:30308, 172.18.0.2:31124, and 172.18.0.2:30308 failed. That means the Windows host agent needs a different path into Wazuh.

Step 4: Use port-forwarding for the Windows host lab

Use kubectl port-forward to expose the Wazuh agent ports to the Windows host on localhost.

PowerShell window 1: registration port

Open a dedicated PowerShell window and run: 

kubectl -n wazuh port-forward --address 127.0.0.1 service/wazuh 1515:1515

Leave this window open.

PowerShell window 2: agent event port

Open a second dedicated PowerShell window and run: 

kubectl -n wazuh port-forward --address 127.0.0.1 service/wazuh-workers 1514:1514

Leave this window open too.

Operator note: These port-forward sessions are part of the lab network path. If either PowerShell window closes, the Windows agent may lose its connection to Wazuh.

Step 5: Prove the Windows host can reach Wazuh

Open a third PowerShell window and test localhost access: 

Test-NetConnection 127.0.0.1 -Port 1515
Test-NetConnection 127.0.0.1 -Port 1514

You want both tests to show: 

TcpTestSucceeded : True

Do not install the Windows agent until these tests pass.

Step 6: Use the Wazuh dashboard Deploy new agent workflow

In this lab, download and install the Windows agent from the Deploy new agent workflow inside your running Wazuh dashboard. This keeps the lab tied to the Wazuh instance you already deployed instead of sending the reader to a separate package page first.

Before using the wizard: Keep both port-forward PowerShell windows from Step 4 running. The Windows agent will use 127.0.0.1 because those port-forward sessions carry localhost traffic into the Kubernetes Wazuh services.

Open the Deploy new agent wizard

  1. Open the Wazuh dashboard.
  2. Go to Endpoints.
  3. Select Deploy new agent.

The wizard has six practical parts. Work through them carefully.

Wizard step 1: Select the package

Under Windows, select: 

MSI 32/64 bits

This tells Wazuh to generate Windows-specific install commands.

Wizard step 2: Server address

In Assign a server address, enter: 

127.0.0.1

This is the correct value for this lab because Windows reaches Wazuh through local port-forwarding.

Do not use Kubernetes DNS here: Do not enter wazuh.wazuh.svc.cluster.local or wazuh-workers.wazuh.svc.cluster.local in the Windows agent wizard. Those names only work from inside Kubernetes pods.

Wizard step 3: Optional settings

You may leave the agent name blank and let Wazuh use the Windows hostname. For a cleaner lab, you can also assign a clear unique name such as: 

windows-host-lab

For groups, use default unless you already created a dedicated Windows lab group.

Agent name note: The agent name must be unique. Do not reuse the Kubernetes node agent name that already appears in Wazuh.

Wizard step 4: Download and install command

After you enter the server address, the wizard generates the Windows download/install command. Copy that command.

Open PowerShell as Administrator, then paste and run the command from the Wazuh dashboard.

Use the command from your dashboard: The dashboard-generated command should include the correct package URL and the server address you entered. Do not copy an old command from a different Wazuh environment.

Manual fallback if you download the MSI yourself

If you choose to manually download the MSI from the wizard and save it locally, use a simple lab folder: 

New-Item -ItemType Directory -Force C:\k8s\wazuh-kubernetes\lab-installers

Save the installer as: 

C:\k8s\wazuh-kubernetes\lab-installers\wazuh-agent.msi

Then install it from an elevated PowerShell window: 

$Installer = "C:\k8s\wazuh-kubernetes\lab-installers\wazuh-agent.msi"

msiexec.exe /i $Installer /q WAZUH_MANAGER="127.0.0.1" WAZUH_REGISTRATION_SERVER="127.0.0.1" WAZUH_REGISTRATION_PORT="1515" WAZUH_PROTOCOL="tcp" WAZUH_AGENT_GROUP="windows-lab"
What this means: The Windows agent sends event traffic to 127.0.0.1:1514 and enrollment traffic to 127.0.0.1:1515. The port-forward sessions carry that traffic into the Wazuh services running in Kubernetes.

Wizard step 5: Start the agent

The dashboard wizard also shows a command to start the Windows agent service. You can use the dashboard-generated command, or run this from elevated PowerShell: 

Start-Service WazuhSvc

If the service already exists and needs to reload configuration, restart it: 

Restart-Service WazuhSvc

Wizard step 6: Verify the agent connection

Return to the Wazuh dashboard and go back to the endpoint list. The Windows host should appear as a new endpoint after the service starts and enrollment completes.

Step 7: Confirm the Windows agent service is running

In elevated PowerShell, confirm the service is running: 

Get-Service WazuhSvc

If the service is not running, start it: 

Start-Service WazuhSvc

Step 8: Start or restart the Windows agent service

Start the Wazuh agent service: 

Start-Service WazuhSvc

If the service already exists and needs to reload configuration, restart it: 

Restart-Service WazuhSvc

Confirm the service is running: 

Get-Service WazuhSvc

Step 9: Check the Windows agent log

The Windows agent log is usually located at: 

C:\Program Files (x86)\ossec-agent\ossec.log

Check the last lines: 

Get-Content "C:\Program Files (x86)\ossec-agent\ossec.log" -Tail 80

Look for successful enrollment, connection, or keepalive messages. If you see connection refused, confirm both port-forward windows are still running and rerun the Test-NetConnection commands from Step 5.

Step 10: Verify the Windows endpoint in Wazuh

Open the Wazuh dashboard and go to the endpoints or agents view. You should now see at least two endpoints:

  • The Kubernetes node agent from the DaemonSet lab.
  • The Windows host agent from this lab.

Confirm the Windows endpoint shows as active. 

Expected evidence:
- Windows endpoint appears in Wazuh
- Status is active
- Operating system is Windows
- Agent version matches the installer
- Recent keepalive or event timestamp is present

Step 11: Generate safe Windows host telemetry

Run simple, benign commands that help create normal endpoint activity. The goal is endpoint visibility, not attacker simulation. 

whoami
hostname
ipconfig
Get-Process | Select-Object -First 5

Create and remove a harmless temporary file: 

New-Item -Path "$env:TEMP\wazuh-lab-test.txt" -ItemType File -Force
Add-Content -Path "$env:TEMP\wazuh-lab-test.txt" -Value "Wazuh Windows host lab test"
Get-Content -Path "$env:TEMP\wazuh-lab-test.txt"
Remove-Item -Path "$env:TEMP\wazuh-lab-test.txt" -Force
Safety boundary: Do not use malware, credential dumping, bypasses, exploit tools, evasion commands, or destructive actions in this lab. Keep the activity benign and focused on visibility.

Step 12: Compare Kubernetes and Windows visibility

In the Wazuh dashboard, compare what each endpoint represents. 

Kubernetes DaemonSet agent:
- Represents the Kubernetes node/container environment
- Helps validate cluster-side monitoring
- Uses in-cluster service DNS

Windows host agent:
- Represents the Windows workstation/host
- Helps validate endpoint-side monitoring
- Uses localhost port-forwarding into Kubernetes

Step 13: Troubleshoot Windows agent enrollment

Port-forward windows are closed

If the port-forward windows close, the Windows agent cannot reach Wazuh through localhost. 

Test-NetConnection 127.0.0.1 -Port 1515
Test-NetConnection 127.0.0.1 -Port 1514

Agent does not appear in Wazuh

Get-Service WazuhSvc
Get-Content "C:\Program Files (x86)\ossec-agent\ossec.log" -Tail 120

Check for enrollment errors, connection refused, authentication failures, or manager address mistakes.

Wrong manager address

For this lab, the Windows agent should use: 

127.0.0.1

It should not use Kubernetes service DNS names such as wazuh.wazuh.svc.cluster.local because those are only valid inside Kubernetes.

Port 1514 or 1515 is already in use

If port-forwarding fails because a local port is already in use, check what is listening: 

Get-NetTCPConnection -LocalPort 1514 -ErrorAction SilentlyContinue
Get-NetTCPConnection -LocalPort 1515 -ErrorAction SilentlyContinue

Stop the conflicting process or choose a different local forwarding approach and update the Windows agent configuration accordingly.

Cleanup note

To stop the Windows host lab path temporarily, close the port-forward PowerShell windows. To remove the Windows Wazuh agent entirely, uninstall it through Windows Apps/Programs or use the Wazuh uninstall guidance for Windows agents.
