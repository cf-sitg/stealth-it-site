Concepts before commands

Troubleshooting starts with lifecycle state: running, exited, created, restarting, or missing.

Logs show application output, but inspect output shows configuration.

Many container problems are command, image, port, mount, or environment problems.

Field note: Do not just run the command. Read the output. Docker teaches you a lot through container names, IDs, ports, status, logs, image tags, and inspect output.

Hands-on lab

Container exits normally

docker run --name exits-lab busybox:latest sh -c "echo starting; echo done"
docker ps -a
docker logs exits-lab

Bad command failure

docker run --name bad-command-lab busybox:latest command-that-does-not-exist
docker ps -a
docker logs bad-command-lab

Port conflict

docker run --name port-lab-1 -d -p 8087:80 nginx:1.27
docker run --name port-lab-2 -d -p 8087:80 nginx:1.27

The second command should fail because the host port is already allocated.

Clean up

docker rm exits-lab bad-command-lab
docker stop port-lab-1
docker rm port-lab-1

Troubleshooting checks

  • Check command output instead of assuming success.
  • Use docker ps -a when something disappears.
  • Use docker logs for app output.
  • Use docker inspect for configuration details.
  • Clean up lab artifacts after testing.

Common mistakes

  • Skipping validation commands.
  • Using latest casually for repeatable work.
  • Leaving containers, volumes, or networks behind.
  • Copying secrets into files or images.
  • Confusing host paths with container paths.

Where this fits in real environments

Real incident response uses the same pattern: capture state, read logs, inspect configuration, identify the failure domain, fix the smallest thing, and validate recovery.
