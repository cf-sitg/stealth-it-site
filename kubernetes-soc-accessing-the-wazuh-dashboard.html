Using the Wazuh Dashboard Like a SOC Analyst

Now that Wazuh is deployed and reachable, use the dashboard with purpose: verify visibility, find alerts, filter by time and source, inspect rule details, capture evidence, and document what the alert means.

What this lesson covers

  • Confirming the dashboard is reachable
  • Validating Wazuh platform visibility
  • Understanding dashboard areas at a high level
  • Reviewing alerts like an analyst
  • Filtering by time, source, rule, and severity
  • Capturing evidence without overreacting
  • Avoiding unsafe or unnecessary dashboard changes

Step 1: Start dashboard access

If your port-forward is not already running, start it again: 

kubectl -n wazuh port-forward --address 127.0.0.1 service/dashboard 8443:443

Open: 

https://127.0.0.1:8443

Login with the lab credentials or the updated credentials you configured after deployment.

Security note: This page assumes local lab access. Do not publish the dashboard broadly, and do not leave default credentials in place for anything persistent, shared, or exposed.

Step 2: Confirm the platform is actually healthy

Before investigating alerts, make sure the dashboard is connected to the rest of the Wazuh platform.

Dashboard checks

  • The dashboard loads without backend connection errors.
  • Wazuh application areas are available.
  • Agent or endpoint sections load.
  • Alert or event views return data once telemetry exists.
  • The dashboard time range is not hiding recent events.

Kubernetes checks

kubectl get pods -n wazuh
kubectl get svc -n wazuh
kubectl get pvc -n wazuh
kubectl get events -n wazuh --sort-by=.lastTimestamp
Analyst note: If the dashboard is unhealthy, an empty alert screen does not mean the lab is quiet. It may mean the platform is not collecting, indexing, or displaying data correctly.

Step 3: Set the right time range

Time range mistakes are common in SIEM work. Before searching, set the dashboard time window to cover the activity you care about.

  • For fresh lab events, start with the last 15 minutes or last 1 hour.
  • For earlier tests, widen the window.
  • Record the time you generated each test event.
  • Be aware of local time vs UTC display differences.

Step 4: Review alerts with a repeatable analyst checklist

Every alert review should answer the same core questions. 

Alert title:
Timestamp:
Agent/source:
Namespace/workload:
Rule ID:
Severity:
Description:
Full log summary:
Expected or unexpected:
Evidence:
Recommended action:

What to look for

  • Timestamp: when the event occurred.
  • Agent/source: where the telemetry came from.
  • Rule ID: which detection or rule fired.
  • Severity: how Wazuh rated it.
  • Description: what Wazuh thinks happened.
  • Full log: the raw or detailed evidence behind the alert.

Step 5: Filter instead of scrolling

Do not treat the dashboard like a long inbox. Filter the data to answer a question.

Useful filter questions

  • Show alerts from the last 30 minutes.
  • Show alerts from a specific agent or workload.
  • Show alerts above a certain severity.
  • Show a specific rule ID.
  • Show activity near the time you generated the lab event.
Analyst note: Filtering is part of the investigation. The question comes first; the filter supports the question.

Step 6: Correlate dashboard evidence with Kubernetes evidence

Wazuh may show an alert, but Kubernetes can help confirm what workload, namespace, pod, or event existed at that time. 

kubectl get pods -A -o wide
kubectl get events -A --sort-by=.lastTimestamp
kubectl logs -n soc-lab <pod-name>
kubectl describe pod -n soc-lab <pod-name>

What correlation helps prove

  • The workload existed at the time of the alert.
  • The pod was running, restarting, or terminating.
  • The source namespace matches the lab activity.
  • Kubernetes events support or contradict the dashboard view.

Step 7: Capture evidence without making assumptions

Evidence is not the same as a conclusion. Capture the alert details first, then decide what they mean. 

Evidence captured:
- Screenshot or copied alert details
- Timestamp
- Agent/source
- Rule ID and severity
- Full log summary
- Kubernetes pod/event/log correlation
- Whether the activity was expected lab activity

Step 8: Know what not to change casually

Avoid making broad dashboard or platform changes while you are learning alert review.

  • Do not suppress alerts globally because they are noisy in a lab.
  • Do not delete users, roles, rules, or index data casually.
  • Do not change passwords without documenting the change.
  • Do not expose the dashboard just to make access easier.
  • Do not confuse expected lab activity with real incident response.

Step 9: Write a short analyst note

Analyst note:
The alert occurred at <time> from <source>.
Wazuh rule <rule_id> reported <description> with severity <level>.
The activity appears expected/unexpected because <evidence>.
Kubernetes correlation showed <pod/namespace/event/log result>.
Recommended action: <close as lab test / tune / investigate further / remediate>.
Bottom line: A SOC dashboard is not the investigation. It is one evidence source. A good analyst combines dashboard context, platform context, and documented reasoning.

Check your understanding

Use these questions to check whether the dashboard workflow is clear before moving forward.

  1. Why should you confirm platform health before investigating alerts?
  2. Why does time range matter in a dashboard investigation?
  3. What is the difference between an alert description and the full log?
  4. Why should you filter instead of scrolling?
  5. What dashboard fields should you capture for an alert?
  6. Why correlate Wazuh evidence with Kubernetes commands?
  7. Why is severity not enough by itself?
  8. Why should you avoid global alert suppression during a lab?
  9. Why should credential changes be documented?
  10. What makes an analyst note useful?
  11. Why should evidence be captured before conclusions?
  12. What does an empty alert view possibly mean besides “nothing happened”?
Answer key
  1. If Wazuh is unhealthy, missing data may reflect a collection, indexing, or dashboard problem rather than a quiet environment.
  2. The dashboard only shows data inside the selected time window, and time zone differences can hide relevant events.
  3. The description summarizes what the rule thinks happened; the full log provides the underlying evidence.
  4. Filtering turns the investigation into a focused question instead of random browsing.
  5. Timestamp, source/agent, rule ID, severity, description, full log summary, and expected/unexpected status.
  6. Kubernetes commands help validate workload, namespace, pod, log, and event context.
  7. Severity needs context, source, evidence, and impact before deciding response.
  8. Suppressing globally can hide useful signal and create blind spots.
  9. So access remains recoverable, auditable, and understandable to future operators.
  10. It states what happened, what evidence supports it, and what action is recommended.
  11. Conclusions should be supported by evidence, not assumptions.
  12. It may mean no telemetry, wrong time range, dashboard/indexer issue, or collection failure.
