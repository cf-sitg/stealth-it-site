Concepts before commands

A container filesystem is tied to the container lifecycle.

A named volume is Docker-managed persistent storage.

A bind mount maps a host path into the container and is useful for labs and development.

Field note: Do not just run the command. Read the output. Docker teaches you a lot through container names, IDs, ports, status, logs, image tags, and inspect output.

Hands-on lab

Create a named volume

docker volume create docker-data-lab
docker volume ls
docker volume inspect docker-data-lab

Write and read persistent data

docker run --name volume-writer -v docker-data-lab:/data busybox:latest sh -c "echo persistent-data > /data/message.txt"
docker rm volume-writer
docker run --name volume-reader -v docker-data-lab:/data busybox:latest cat /data/message.txt

Bind mount current folder

mkdir bind-mount-lab
cd bind-mount-lab
echo Hello from host > message.txt
docker run --rm -v ${PWD}:/data busybox:latest cat /data/message.txt

Clean up

docker rm volume-reader
docker volume rm docker-data-lab

Troubleshooting checks

  • Check command output instead of assuming success.
  • Use docker ps -a when something disappears.
  • Use docker logs for app output.
  • Use docker inspect for configuration details.
  • Clean up lab artifacts after testing.

Common mistakes

  • Skipping validation commands.
  • Using latest casually for repeatable work.
  • Leaving containers, volumes, or networks behind.
  • Copying secrets into files or images.
  • Confusing host paths with container paths.

Where this fits in real environments

Persistent storage is one of the biggest differences between disposable application containers and stateful services. Kubernetes later uses volumes and claims for similar lifecycle separation.
